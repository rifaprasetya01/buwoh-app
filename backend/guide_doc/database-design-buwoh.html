Ringkasan Sistem
System Overview & Context

Platform Buwoh adalah aplikasi berbasis web/mobile yang memfasilitasi tradisi buwoh (gotong-royong membawa bawaan ke hajatan) secara digital. Platform ini menghubungkan pemilik acara (hajatan, khitan, pernikahan) dengan tamu yang ingin berpartisipasi dengan membawa bawaan.

🎯 Scope MVP
  • Registrasi & autentikasi user
  • Manajemen acara (CRUD)
  • Pengajuan & persetujuan tamu
  • Pencatatan detail bawaan tamu
  • Verifikasi kehadiran di lokasi
  • Sistem notifikasi balas budi
  • Dashboard pemilik acara
  • Riwayat acara yang dihadiri
👥 Peran User
  • User sebagai Pemilik Acara
  • User sebagai Calon Tamu
  • Satu user bisa memiliki kedua peran
  • Tidak ada role admin terpisah (MVP)
  • Pemilik acara bisa buat rekomendasi bawaan
  • Pemilik acara bisa verifikasi kehadiran
📌 Keputusan Desain Awal
Database menggunakan pendekatan RDBMS (Relational Database) seperti PostgreSQL atau MySQL. Dipilih karena data memiliki relasi yang kuat antar entitas, memerlukan transaksi yang konsisten (ACID), dan skala kecil-menengah tidak memerlukan NoSQL.
2
Entitas & Relasi (ERD Overview)
Entity Relationship Diagram – Tekstual

Sistem terdiri dari 9 tabel utama yang saling berelasi. Berikut gambaran lengkap relasi antar entitas:

users
↳ 1 : N membuat → events (satu user bisa punya banyak acara, tidak boleh bertabrakan waktu)
↳ 1 : N mengajukan → event_guests (satu user bisa jadi tamu di banyak acara)
↳ 1 : N menerima → notifications

events
↳ N : 1 bertipe → event_categories
↳ 1 : N memiliki → event_guests (daftar tamu yang mengajukan)
↳ 1 : N memiliki → event_gift_recommendations (rekomendasi bawaan dari pemilik)

event_guests
↳ 1 : N memiliki → guest_gifts (detail bawaan yang dibawa tamu)

guest_gifts
↳ N : 1 dikategorikan ke → gift_categories (beras, uang, gula, dll)

event_gift_recommendations
↳ N : 1 merujuk ke → gift_categories

notifications
↳ N : 1 terkait → events (notifikasi balas budi terkait acara tertentu)
↳ N : 1 ditujukan ke → users
💡 Tabel yang Ditambahkan vs Diusulkan Klien
Klien mengusulkan: users, events, buwoh/buwohan, kategori buwoh, kategori acara.

Perubahan & penambahan:
✅ "Buwohan" dipecah menjadi event_guests (data tamu) dan guest_gifts (detail bawaan) — agar satu tamu bisa membawa lebih dari satu jenis bawaan.
✅ Ditambahkan tabel event_gift_recommendations untuk fitur rekomendasi bawaan dari pemilik acara.
✅ Ditambahkan tabel notifications untuk fitur balas budi.
✅ Semua tabel dilengkapi timestamp created_at dan updated_at untuk audit trail.

⚠️ Business Rule – Anti-Tabrakan Jadwal
Validasi tidak boleh dilakukan hanya di level database constraint karena SQL standar tidak mendukung range overlap check secara langsung. Validasi wajib dilakukan di application layer sebelum INSERT/UPDATE, dengan query: WHERE user_id = ? AND status != 'cancelled' AND start_datetime < ? AND end_datetime > ?. Lakukan juga pengecekan ini sebelum user bisa mempublish acara (status: draft → published).

Alur Bisnis & State Diagram
Business Flow & State Transitions

Alur Pengajuan Tamu (Proses Utama)

User B lihat acara
→
Isi form bawaan (guest_gifts)
→
Submit pengajuan
(status: pending)
→
User A terima/tolak
→
Hari-H: verifikasi hadir
→
Cek kesesuaian bawaan

State Diagram: events.status

draft → publish → published → hari-H → ongoing → selesai → completed
cancelled ← bisa dari state draft, published, atau ongoing

State Diagram: event_guests.application_status

pending → pemilik terima → accepted → hari-H → cek attendance_status
pending → pemilik tolak → rejected

Alur Balas Budi (Trigger Notifikasi)

🔔 Kapan Notifikasi Balas Budi Dibuat?
Ketika User B mempublish acara baru (events.status berubah dari 'draft' → 'published'), sistem harus:

1. Cari semua user yang pernah hadir di acara User B (event_guests WHERE user_id = B AND attendance_status = 'present').
2. Buat notifikasi bertipe 'balas_budi' untuk masing-masing user tersebut.
3. Isi: "Si X baru saja membuat acara [nama acara]. Kamu pernah hadir di acaranya. Waktunya balas budi!"

Logika ini dijalankan di application layer (bukan trigger database) agar lebih mudah dikontrol dan di-test.

Business Rules & Constraint
Aturan Bisnis yang Wajib Diterapkan
#Aturan BisnisDiterapkan DiDetail
BR-01 Satu user tidak boleh punya acara bertabrakan jadwal Application Layer Cek overlap sebelum INSERT/UPDATE event. Acara berstatus 'cancelled' dikecualikan.
BR-02 User tidak bisa mendaftar ke acara miliknya sendiri Application Layer Cek event.user_id != current_user_id sebelum membuat event_guests.
BR-03 Satu user hanya bisa mengajukan sekali per acara DB Constraint UNIQUE KEY (event_id, user_id) pada tabel event_guests.
BR-04 Form bawaan wajib diisi sebelum pengajuan dikirim Application Layer Minimal harus ada 1 baris di guest_gifts sebelum application_status diset ke 'pending'.
BR-05 Bawaan tidak bisa diubah setelah pengajuan diterima Application Layer Cek application_status == 'pending' sebelum mengizinkan edit guest_gifts.
BR-06 Jumlah tamu tidak boleh melebihi max_guests Application Layer Cek count accepted guests < max_guests sebelum menerima pengajuan baru. Berlaku jika max_guests tidak NULL.
BR-07 Verifikasi kehadiran hanya bisa dilakukan pemilik acara Application Layer Pastikan user yang melakukan request adalah pemilik events yang bersangkutan.
BR-08 quantity pada guest_gifts harus > 0 DB Constraint Tambahkan CHECK constraint: CHECK (quantity > 0).

Indeks & Optimasi Query
Database Indexing Strategy

Berikut daftar indeks yang direkomendasikan untuk performa optimal pada query-query yang paling sering dijalankan:

  • IDX-01 events → (user_id, status) — untuk query dashboard acara milik user dan filter berdasarkan status
  • IDX-02 events → (start_datetime, end_datetime) — untuk validasi overlap jadwal dan query acara berdasarkan rentang waktu
  • IDX-03 events → (event_category_id) — untuk filter acara berdasarkan kategori
  • IDX-04 event_guests → (event_id, application_status) — untuk query daftar tamu per acara berdasarkan status
  • IDX-05 event_guests → (user_id, application_status) — untuk riwayat acara yang dihadiri user tertentu
  • IDX-06 guest_gifts → (event_guest_id) — untuk mengambil bawaan milik satu pengajuan tamu
  • IDX-07 notifications → (recipient_user_id, is_read) — untuk query notifikasi belum dibaca milik user
  • IDX-08 notifications → (type, related_event_id) — untuk mencegah duplikasi notifikasi balas budi

Contoh Query Utama
Sample SQL Queries untuk Fitur-Fitur Utama
Q1 — Dashboard: Daftar Acara Milik User (dengan ringkasan tamu)
-- Dashboard pemilik acara: semua acara beserta jumlah tamu diterima
SELECT
    e.id, e.title, e.status,
    e.start_datetime, e.end_datetime,
    e.location_name,
    ec.name AS category_name,
    COUNT(eg.id) AS total_applicants,
    SUM(CASE WHEN eg.application_status = 'accepted' THEN 1 ELSE 0 END) AS total_accepted,
    SUM(CASE WHEN eg.attendance_status = 'present' THEN 1 ELSE 0 END) AS total_hadir
FROM events e
LEFT JOIN event_categories ec ON e.event_category_id = ec.id
LEFT JOIN event_guests eg ON e.id = eg.event_id
WHERE e.user_id = :user_id
GROUP BY e.id
ORDER BY e.start_datetime DESC;
Q2 — Detail Tamu + Bawaan Lengkap untuk Satu Acara
-- Detail semua tamu acara beserta rincian bawaannya
SELECT
    u.name AS guest_name,
    u.phone_number,
    eg.application_status,
    eg.attendance_status,
    eg.gift_verified,
    gc.name AS gift_type,
    gg.quantity,
    gc.unit,
    gg.notes AS gift_notes
FROM event_guests eg
JOIN users u ON eg.user_id = u.id
JOIN guest_gifts gg ON eg.id = gg.event_guest_id
JOIN gift_categories gc ON gg.gift_category_id = gc.id
WHERE eg.event_id = :event_id
ORDER BY u.name, gc.name;
Q3 — Riwayat: Acara yang Pernah Dihadiri User
-- Riwayat acara yang pernah user datangi beserta bawaannya
SELECT
    e.title AS event_title,
    e.start_datetime,
    ec.name AS event_category,
    owner.name AS event_owner,
    eg.attendance_status,
    gc.name AS gift_type,
    gg.quantity,
    gc.unit
FROM event_guests eg
JOIN events e ON eg.event_id = e.id
JOIN event_categories ec ON e.event_category_id = ec.id
JOIN users owner ON e.user_id = owner.id
JOIN guest_gifts gg ON eg.id = gg.event_guest_id
JOIN gift_categories gc ON gg.gift_category_id = gc.id
WHERE eg.user_id = :user_id
  AND eg.application_status = 'accepted'
ORDER BY e.start_datetime DESC;
Q4 — Validasi Anti-Tabrakan Jadwal
-- Cek apakah user sudah punya acara di rentang waktu yang diinginkan
-- Jika query ini mengembalikan baris, maka jadwal bertabrakan (TOLAK)
SELECT id, title, start_datetime, end_datetime
FROM events
WHERE user_id = :user_id
  AND status NOT IN ('cancelled')
  AND start_datetime < :new_end_datetime
  AND end_datetime > :new_start_datetime
LIMIT 1;
Q5 — Trigger Balas Budi: Siapa yang Perlu Dinotifikasi?
-- Ketika user X publish acara baru (event_id = :new_event_id),
-- cari semua user yang pernah hadir di acara milik user X
SELECT DISTINCT
    eg.user_id AS recipient_user_id
FROM event_guests eg
JOIN events e ON eg.event_id = e.id
WHERE e.user_id = :event_owner_id          -- acara milik si pemilik
  AND eg.attendance_status = 'present'    -- yang pernah hadir
  AND eg.user_id != :event_owner_id;       -- bukan dirinya sendiri
-- Kemudian buat baris di tabel notifications untuk tiap user di atas

Catatan & Rekomendasi
Notes, Recommendations & Future Considerations
🛠️ Teknologi yang Direkomendasikan
  • PostgreSQL 15+ — lebih robust untuk produksi
  • MySQL 8+ — jika tim lebih familiar
  • Gunakan ORM seperti Prisma, Eloquent, atau TypeORM
  • Migrasi database: gunakan tools seperti Flyway atau migrasi bawaan framework
🔐 Keamanan Data
  • Selalu hash password dengan bcrypt/argon2 (cost factor ≥ 12)
  • Jangan simpan token sesi di database (gunakan JWT atau Redis)
  • Semua input user wajib di-sanitize sebelum query
  • Gunakan parameterized query (hindari raw SQL dengan string concat)
📈 Potensi Pengembangan Fitur
  • Fitur chat antara pemilik acara dan tamu
  • Rating/review setelah acara selesai
  • Rekap statistik total bawaan per acara
  • Fitur undangan digital (share link acara)
  • Notifikasi push (Firebase/OneSignal)
  • Laporan PDF rekapitulasi tamu & bawaan
⚠️ Hal yang Perlu Dikonfirmasi Ulang
  • Apakah data master gift_categories bisa ditambah oleh user, atau hanya oleh admin?
  • Apakah event yang sudah 'completed' bisa dihapus?
  • Berapa lama data notifikasi disimpan?
  • Apakah diperlukan fitur soft-delete (hapus data tapi tidak permanen)?
✅ Ringkasan Tabel Final
Total 8 tabel dirancang: users, event_categories, events, event_gift_recommendations, gift_categories, event_guests, guest_gifts, notifications. Semua relasi menggunakan Foreign Key dengan ON DELETE yang perlu dikonfirmasi (disarankan: RESTRICT untuk data finansial, CASCADE untuk data turunan langsung).
